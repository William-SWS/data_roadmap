    1. Overview

    Subject: the full stack of modern data work, covering every node in the attached roadmap: Python engineering, backend services, databases, analysis, machine learning, deep learning, MLOps, big-data systems, cloud architecture, system design, production operations and advanced AI systems (LLMs, RAG, agents).

    Target level: Level 3, Independent, as a full-stack data professional. You will be able to choose and defend the right tool or pattern for a new situation across the stack. Depth varies on purpose (see the per-phase targets in §4). Topics you can only emulate locally (managed cloud services) or that are rarely needed in data platforms (GANs, reinforcement learning) are held at Level 2 or survey level, and the plan says so wherever that applies.

    Duration and load: 52 weeks, about 700 core hours (≈ 13.5 h/week), inside your 15–20 h/week range. There is a cut list for weeks when you have less time (§4.1).

    By the end you will be able to build, secure, deploy, operate and evolve a data platform end to end: from a typed Python package to a Kubernetes-hosted ML service with drift monitoring, a lakehouse fed by streams, infrastructure as code, SLO-based operations and an evaluated retrieval-augmented assistant. You will also be able to explain the trade-offs behind each choice.

    Final project in one sentence: CareFlow v3, a production-style hospital-operations data and AI platform built on synthetic health records, delivered as a public repository, a design report, runbooks, model and data documentation, and a live demo.

    4.1 Workload audit

    Method. Each week was estimated with the playbook's rates: dense paper 1.5–3 h, book chapter 1–2 h, lecture runtime × 1.3, a 1,000-word analytical deliverable 2–4 h, a substantial artefact 4–10 h. Totals were summed per week, then for the plan.

    Result. Core plan ≈ 700 h (≈ 13.5 h/week); the heaviest week is W32 (15 h). Stated capacity is 780–1,040 h. Discounted by 20–30% for illness, travel, work spikes and drift, that becomes ≈ 546–832 h. At the middle of your range (17.5 h/week) the plan keeps a ≈ 23% buffer, which is within the playbook's band. At a steady 15 h/week the buffer is only ≈ 10%, so plan on using the cuts below.

    Cut list (apply in the playbook's order; practical tasks are cut last):

    1. Optional readings: already outside the core hours. Don't add them if you are behind.
    2. Overlapping and revisit sources (≈ −25 h → ≈ 675 h): skip every source marked "Revisit" (about 10 h). Skip the parallel course modules that duplicate a core text: ML Zoomcamp in W18, Google MLCC in W19, fast.ai in W23, 3Blue1Brown in W22, DE Zoomcamp in W33/W40, MLOps Zoomcamp in W21/W28, LLM Zoomcamp in W47 (about 15 h).
    3. Breadth (≈ −50 h → ≈ 625 h): W11 drop the graph variant (−2); W12 drop CDC (−2); W19 drop association rules (−1); W22 skip micrograd and go straight to PyTorch (−3); W24 drop the LSTM rung (−1.5); W25 decision matrix only, no autoencoder (−4); W26 drop DDP and cut the experiments to two variables (−4); W30 replace Feast with a tested SQL feature layer (−3); W35 drop the schema registry (−1); W36 shorten the cluster runbook (−3); W38 drop the Moto function (−1.5); W39 service map only, no local TLS/ingress (−4); W40 drop the Moto provider (−1.5); W44 drop tracing (−1.5); W45 simplify the cost report (−2); W49 drop fine-tuning, keep the workflow (−4); W16 and W27 halve the walkthrough and ADR work (−6); W21 skip the latency target work (−1); W41 load test only, no fifth ADR (−2); W47 one chunking strategy (−1.5).
    4. Task depth, last (≈ −40 h → ≈ 585 h): halve counts (SQL queries 12→6, models 6→4, golden set 60→30, forecasts and prompts similarly), shorten written deliverables by about a third, and cut the capstone report to 3,000 words.

    If you are still over after all cuts: extend to 56–60 weeks rather than dropping practice, or lower Phases 8–9 to Level 2 by keeping designs and benchmarks and skipping the cluster and IaC builds. Decide at the W16 or W27 review.

    Diagnostic, development environment and the CareFlow repository

    W0113 h coreTask level 1/5

    Roadmap topics: Core Language Syntax, Data Structures, Development Environment

    Main focus: Prove what you already know in core Python, fill only the gaps, and set up the tools and repository you will use for 52 weeks.

    What you will understand:

    • Where your Python gaps actually are, measured against the roadmap rather than guessed
    • Shell, Git branching and remote workflows, issues and code review as daily habits
    • How the running case (CareFlow on Synthea synthetic health records) is structured

    Why it matters: You are experienced, so this plan does not reteach syntax. A short, honest diagnostic protects the time you will need for MLOps, cloud and AI systems later. The repository you create this week becomes the portfolio artefact for the whole year.

    Prerequisites: None (starting point).

    Recommended sources:

    1. ★ MIT CSAIL. The Missing Semester of Your CS Education (2026 edition; earlier 2020 edition). S001 — university course + videos, free. Link
      • Why it's here: A compact, modern course on the tools a professional uses every day. The 2026 edition adds agentic coding and code quality.
      • How to use it: Watch lectures 1, 2, 3 and 5 (shell, command-line environment, dev environment, Git). Skip anything you already use fluently.
      • Caveat: Tool-focused; it teaches habits, not software design.
    2. Chacon, S., & Straub, B. (2014). Pro Git (2nd ed.). Apress. S002 — book, free online (cc by-nc-sa 3.0). Link
      • Why it's here: The standard free Git reference, useful when a workflow breaks.
      • How to use it: Read ch. 3 (Branching) and ch. 5 (Distributed Git). Keep ch. 7 (Git Tools) for reference.
      • Caveat: 2014 edition. Newer commands such as git switch and git restore are not covered.
    3. Walonoski, J., et al. / MITRE. Synthea: Synthetic Patient Population Simulator (GitHub repository, Apache-2.0). S003 — open-source tool + data generator, free (apache 2.0). Link
      • Why it's here: Synthea generates realistic but fictional patient records, so you can build a health-data platform without privacy risk.
      • How to use it: Follow the README: install Java 17+, then generate 1,000 patients with CSV export and a fixed seed.
      • Caveat: Synthetic data follows Synthea's modules, not real clinical practice. Findings about 'patients' are findings about the simulator.

    Estimated time: reading/video 4 h · task 8 h · reflection 1 h · total 13 h

    Week 2 of 52 · Phase 1 · Python Fundamentals

    Advanced language features and object-oriented design

    W0213.5 h coreTask level 2/5

    Roadmap topics: Advanced Language Features, Object Oriented Programming

    Main focus: Use generators, iterators, decorators, context managers, typing and Python's data model to write a clean ingestion library for CareFlow.

    What you will understand:

    • The iterator protocol and lazy evaluation for files too large for memory
    • Decorators and context managers as reusable cross-cutting behaviour
    • Classes, inheritance vs composition, abstract base classes and dunder methods, and when not to use classes

    Why it matters: Everything you build later (APIs, pipelines, feature code) sits on these features. Streaming a 1 GB CSV with generators instead of loading it is the first scalability decision you will make.

    Prerequisites: Week 1.

    Recommended sources:

    1. ★ Kuchling, A. M. Functional Programming HOWTO. Python documentation (3.14). S004 — official documentation, free. Link
      • Why it's here: The official explanation of iterators, generators, itertools and functools, written by a CPython core developer.
      • How to use it: Read the sections on iterators, generators (including send) and the itertools/functools modules.
      • Caveat: It does not cover async generators.
    2. Python Software Foundation. 3. Data model (The Python Language Reference, 3.14). S005 — official documentation, free. Link
      • Why it's here: The language reference for special methods; this is where Python's OOP 'magic' is actually defined.
      • How to use it: Read the parts on special method names, emulating containers and context managers.
      • Caveat: Reference style, not a tutorial. Use it to look things up.
    3. Python Typing Team. Static Typing with Python (typing.python.org). S006 — official documentation, free. Link
      • Why it's here: The official typing guide. It also includes a page on reasons to avoid static type checking, which is a useful dissenting view.
      • How to use it: Read the typing best-practices guide and the 'Reasons to avoid static type checking' page.
      • Caveat: Type-checker behaviour (mypy vs pyright) differs in the details.

    Estimated time: reading/video 4.5 h · task 8 h · reflection 1 h · total 13.5 h

    Practical task — CareFlow ingestion library (level 2)

    • Deliverable: A careflow.ingest package that streams Synthea CSVs with generators, validates rows into typed models (dataclasses or Pydantic), uses a context manager for file/DB handles and a decorator for timing and retry, and exposes a top_k_costly_encounters(k) function built on heapq.
    • Input: Synthea CSV output from Week 1.
    • Constraint: Peak memory must stay under 200 MB while processing the largest CSV. Measure it and record the figure.
    • Quality bar: Type-checks cleanly with no Any in public functions; each dunder method you add has a test showing why it is needed.
    • Time: 8 h

    Reflection questions:

    1. Where did you choose a class when a function would have done? Why?
    2. Which of the 'reasons to avoid static typing' apply to CareFlow, if any?

    Discussion question:

    1. Is inheritance ever the right default in data-engineering code, or should composition always win?

    Evidence of completion: careflow.ingest package with tests and a memory-measurement note.

    Checkpoint:

    • I can write a generator pipeline and explain when it is evaluated.
    • I can implement a context manager and a parameterised decorator from memory.
    • I can apply these patterns to a non-data codebase (e.g. a CLI tool).
    • I can name a case where generators hurt (e.g. data needed twice, or debugging lazy errors).
    • If not: Reread the generators section of the Functional Programming HOWTO; rebuild the reader for one CSV with an explicit iterator class.

      • Caveat: Keep CareFlow public to stay free, or run the same steps locally with pre-commit.

    Frameworks and models

    REST (Fielding, 2000)

    REST (Fielding, 2000) (W5)

    Field Appraisal
    Origin Roy Fielding's dissertation (UC Irvine, 2000), abstracting the Web's architecture.
    Core claim A set of constraints (client–server, stateless, cacheable, uniform interface, layered) yields scalable, evolvable network systems.
    Evidence base The Web itself. Most "REST APIs" adopt only some constraints.
    Strengths Shared vocabulary; caching and statelessness scale well.
    Limitations Full hypermedia rarely pays off for internal APIs; streaming and RPC-style needs fit poorly.
    Best used when Resource-oriented public or partner APIs.
    Avoid when Low-latency internal calls with strict contracts (consider gRPC, W29).
    Rivals gRPC/RPC, GraphQL, event-driven integration.

    Frameworks and models

    Twelve-Factor App

    Twelve-Factor App (W7–8, W16)

    Field Appraisal
    Origin Heroku engineers (Adam Wiggins et al.), 2011, last updated 2017.
    Core claim Twelve practices (config in the environment, stateless processes, disposability and others) make services portable and scalable.
    Evidence base Practitioner consensus; not empirically tested.
    Strengths A simple audit checklist; aligns with containers.
    Limitations Predates Kubernetes and secret managers; silent on data-intensive and stateful services.
    Best used when Stateless web services and workers.
    Avoid when Databases, streaming state stores, ML training jobs with large local state.
    Rivals Cloud-native frameworks (e.g. the AWS Well-Architected pillars).

    Frameworks and models

    Relational model and normalisation

    Relational model and normalisation (W9–10)

    Field Appraisal
    Origin E. F. Codd (1970); taught here through CMU 15-445.
    Core claim Data as relations with declarative queries and integrity constraints; normalisation removes update anomalies.
    Evidence base Five decades of dominance; Stonebraker & Pavlo (2024) argue alternatives keep converging back to it.
    Strengths Integrity, declarative optimisation, a mature ecosystem.
    Limitations Rigid schemas for sparse or evolving data; joins cost at extreme scale.
    Best used when Operational data with integrity needs (e.g. clinical records).
    Avoid when Access is purely by key at huge scale, or documents are self-contained.
    Rivals Document, key-value, wide-column and graph models (W11).

    Frameworks and models

    Dimensional modelling (Kimball)

    Dimensional modelling (Kimball) (W10, W15)

    Field Appraisal
    Origin Ralph Kimball; The Data Warehouse Toolkit (3rd ed.).
    Core claim Facts at a declared grain plus conformed dimensions give understandable, fast analytics.
    Evidence base Long industry use; practitioner evidence.
    Strengths Business-readable; clear metric semantics (additivity).
    Limitations Upfront modelling effort; lakehouse and "one big table" styles challenge it.
    Best used when BI and shared metrics.
    Avoid when Exploratory data science on raw events.
    Rivals Data vault, wide denormalised tables, semantic layers over normalised data.

    Frameworks and models

    CAP and consistency models

    CAP and consistency models (W11, W42)

    Field Appraisal
    Origin Brewer's conjecture (2000), formalised by Gilbert & Lynch; revisited by Brewer (2012).
    Core claim During a network partition a system must trade consistency (linearizability) against availability.
    Evidence base Formal proof for its narrow definitions.
    Strengths Makes partition behaviour an explicit design choice.
    Limitations "CP/AP" labels mislead (Kleppmann 2015); ignores latency and the many consistency levels (Jepsen map).
    Best used when Reasoning about behaviour during failures.
    Avoid when Classifying products by a single label.
    Rivals PACELC-style latency/consistency framing; precise isolation and consistency models.

    Frameworks and models

    Bias–variance and the classical ML workflow

    Bias–variance and the classical ML workflow (W17–20)

    Field Appraisal
    Origin Statistical learning theory; taught through ISLP.
    Core claim Generalisation error trades bias against variance; validation must mirror deployment.
    Evidence base Strong theoretically and empirically. Leakage undermines many published results (Kapoor & Narayanan).
    Strengths A principled basis for model choice and validation design.
    Limitations Deep-learning "double descent" complicates the simple picture; the theory is silent on leakage and drift.
    Best used when Tabular prediction problems like readmission.
    Avoid when You treat cross-validation scores as deployment performance without temporal checks.
    Rivals Deep learning as a default (disputed on tabular data by Grinsztajn et al.).

    Transformer architecture

    Transformer architecture (W24, W46)

    Field Appraisal
    Origin Vaswani et al. (2017).
    Core claim Self-attention without recurrence models sequences better and trains in parallel.
    Evidence base Dominant across NLP and increasingly vision and multimodal work.
    Strengths Scales with data and compute; transfer learning.
    Limitations Quadratic attention cost; long-context use is imperfect (Lost in the Middle); compute-hungry.
    Best used when Language tasks with enough data or a pretrained model.
    Avoid when Small tabular or simple text tasks where TF-IDF or trees suffice (your W24 ladder tests this).
    Rivals RNNs/LSTMs historically; state-space models; classical NLP baselines.

    ML technical debt and the ML Test Score

    ML technical debt and the ML Test Score (W27, W32)

    Field Appraisal
    Origin Sculley et al. (2015); Breck et al. (2017), Google.
    Core claim ML systems accumulate hidden debt (entanglement, data dependencies, glue code); 28 tests measure readiness.
    Evidence base Practitioner experience at Google; interview evidence (Shankar et al., 2022) supports the pain points.
    Strengths Actionable checklist; a shared vocabulary for debt.
    Limitations Self-scored; Google-scale assumptions.
    Best used when Deciding what to automate or test next.
    Avoid when You treat the score as a certificate of safety.
    Rivals MLOps maturity models from vendors and cloud providers.

    Lakehouse

    Lakehouse (W34)

    Field Appraisal
    Origin Armbrust et al., CIDR 2021 (Databricks).
    Core claim Open file formats plus a transactional metadata layer can replace separate lakes and warehouses.
    Evidence base Vendor benchmarks; wide industry adoption of Iceberg and Delta.
    Strengths One copy of data for BI and ML; open formats.
    Limitations Operational complexity (small files, compaction, catalogs); vendor authorship.
    Best used when Large, multi-consumer analytical data.
    Avoid when Data fits comfortably in one database or DuckDB (W33, W36).
    Rivals Cloud warehouses; single-node analytics ("big data is dead").

    Frameworks and models

    Dataflow model and the log

    Dataflow model and the log (W35)

    Field Appraisal
    Origin Kreps (2013); Akidau et al., PVLDB (2015).
    Core claim Treat data as unbounded, out-of-order streams; separate what, where (windows), when (watermarks, triggers) and how (refinement).
    Evidence base Basis of Apache Beam, Flink and Spark Structured Streaming semantics.
    Strengths Correctness with late data; unifies batch and stream.
    Limitations Watermarks are heuristic; operational complexity.
    Best used when Event-time analytics with late or duplicate events.
    Avoid when Minute-level freshness is enough; use micro-batch SQL instead.
    Rivals Periodic batch; lambda architecture.

    SRE and SLOs

    SRE and SLOs (W31, W44–45)

    Field Appraisal
    Origin Google SRE (SRE Book 2016, Workbook 2018).
    Core claim Define reliability as SLOs; spend error budgets deliberately; alert on symptoms; learn through blameless post-mortems.
    Evidence base Wide industry adoption; mostly practitioner evidence.
    Strengths Makes reliability negotiable in numbers.
    Limitations Ceremony-heavy for small teams; SLOs can drive the wrong behaviour if badly chosen.
    Best used when User-facing services with measurable journeys.
    Avoid when You cannot measure user-perceived reliability yet.
    Rivals Traditional ITIL-style operations; uptime-only targets.

    Frameworks and models

    Retrieval-augmented generation and workflows vs agents

    Retrieval-augmented generation and workflows vs agents (W47–49)

    Field Appraisal
    Origin Lewis et al. (2020) for RAG; ReAct (2022); Anthropic's "Building effective agents" (2024).
    Core claim Ground generation in retrieved sources; prefer predefined workflows, and use autonomous agents only where open-ended tasks need them.
    Evidence base Strong for RAG improving factuality on knowledge tasks; agent reliability evidence is still early.
    Strengths Answers cite sources; knowledge updates without retraining.
    Limitations Retrieval quality caps answer quality; long contexts are used unevenly; agents amplify errors and security risks (OWASP LLM06 excessive agency).
    Best used when Question answering over changing internal documents.
    Avoid when The task needs guaranteed correctness with no human review.
    Rivals Fine-tuning; long-context prompting; classical search.

    Critical discussions

    7.1 Monolith first or services first?

    The plan does not settle these for you. Each one ends with what a practitioner can reasonably do while the question stays open, and each is tested on CareFlow.

    • Monolith first: Fowler S132. Almost all microservice successes started as a monolith; boundaries need domain knowledge first.
    • Services first: Tilkov S133. Monoliths couple parts so tightly they can't be split later.
    • Practitioner stance: build a modular monolith with explicit boundaries (Cosmic Python ch. 1–7), measure pain points, and split only along boundaries you can justify (W41 ADRs).

    Critical discussions

    7.2 Relational vs NoSQL

    • Relational wins over time: Stonebraker & Pavlo S033. Alternatives are niche or converging to SQL.
    • Model by access pattern: MongoDB's modelling guidance S032; Dynamo's availability-first design S039.
    • Practitioner stance: benchmark the real access pattern and state the consistency guarantee you need (W11 memo). Default to PostgreSQL (with JSONB/pgvector) unless evidence says otherwise.

    Critical discussions

    7.3 Do you have big data?

    • Distributed by default: MapReduce/Spark papers S103, S102; the lakehouse S107.
    • Single node first: COST S105; "Big Data is Dead" S118.
    • Practitioner stance: always benchmark against a strong single-node baseline (W33, W36), and adopt clusters only past a measured threshold.

    Critical discussions

    7.4 Cloud or on-premises?

    • Cloud: elasticity, managed services, Well-Architected practices S119.
    • Repatriation: DHH S123; a16z's cost paradox S124.
    • Practitioner stance: decide per workload using cost models, skills and compliance (LGPD for health data); keep infrastructure as code portable (W37, W40).

    Critical discussions

    7.5 Deep learning vs simpler models, and the limits of deep learning

    • Trees win on tabular data: Grinsztajn et al. S057. Leakage inflates "complex beats simple" claims S055.
    • Deep learning's broader limits: Marcus S080; counterpoint: transformers' success across language and vision S074.
    • Practitioner stance: always run the baseline ladder (W18, W22, W24, W49) and report compute cost next to accuracy.

    Critical discussions

    7.6 Agents, RAG and evaluation

    • Start simple: workflows before agents S161; RAG grounding S150 vs long context, which is used unevenly S153.
    • Can LLMs judge LLMs? They agree with humans over 80% of the time in some settings but show position, verbosity and self-enhancement biases S155.
    • Practitioner stance: measure judge–human agreement on your own data, red-team for prompt injection S156, and keep autonomy minimal in clinical contexts (W48–49).

    Critical discussions

    7.7 Smaller disputes you will meet

    • Static typing in Python: strongly recommended in this plan, but the official typing guide lists reasons to avoid it S006.
    • p-values: ASA principles S050 vs everyday "significant/not significant" reporting; report effect sizes and intervals (W14).
    • CAP labels: helpful primer framing S129 vs "please stop calling databases CP or AP" S137.
    • Feature stores: point-in-time correctness S091 vs the operating cost of another system (W30 ADR).

    13. Final project — CareFlow v3

    Brief. A regional network of hospitals (simulated with Synthea) wants a data and AI platform for operations. It needs trustworthy operational data, dashboards for ward managers, a readmission-risk model that clinicians can scrutinise, real-time bed occupancy, and an assistant that answers staff questions about the platform itself. You are the full-stack data professional building it. CareFlow v3 is that platform.

    Deliverables.

    1. Public repository with a one-command local deployment (OpenTofu + kind + Compose where needed) and seeded synthetic data.
    2. Design report, 4,000–5,000 words: architecture (C4), ADR index, trade-off table, data model, ML lifecycle, scale choices with benchmarks, cloud design with cost model, reliability and security, AI assistant evaluation, and limitations.
    3. Runbooks: deployment and rollback, disaster recovery (PITR), incident response, maintenance schedule, model retraining.
    4. Model card, datasheet, LGPD art. 20 review procedure, transparency note for the assistant.
    5. A 15–20 minute demo with Q&A, to a peer group, mentor or study group.
